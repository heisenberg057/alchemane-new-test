# Backend Production Hardening Plan (Full Change List)

Scope:
- Backend only: `/AmericanHairline-Unified/backend`
- Production target: Docker / docker-compose (NOT Railway)
- Goal: make backend end-to-end working + production-ready (reliable, secure, observable, deployable)

## 1) Full list of backend mismatches / gaps (as-is)

### Deployment & runtime
- Port defaults are inconsistent:
  - `src/index.js` defaults to 3000
  - `src/config/env.js` defaults to 5001
  - `.env.example`, Dockerfile EXPOSE, docker-compose expect 5000
  - Risk: health checks fail, container exposes wrong port, platform routing breaks.
- Docker healthcheck assumes the app listens on 5000; this is fragile given port mismatch.
- Logging writes to `logs/*.log` but Docker runs as non-root and does not create a writable `logs/` directory; file transports can fail or drop logs.
- Railway artifacts exist but are obsolete for current target:
  - `railway.json` refers to `start:prod` which doesn’t exist in backend `package.json`
  - `migrate-and-start.js` is Railway-oriented and unsafe (see DB section).

### Database & Prisma (CRITICAL)
- Prisma provider mismatch:
  - `prisma/schema.prisma` currently uses sqlite provider
  - `docker-compose.yml` uses Postgres URL
  - Repo includes `prisma/schema.postgres.prisma` and `MIGRATION_GUIDE.md` describing sqlite→postgres, so the main schema is not aligned with intended production.
- Unsafe production migration path:
  - `migrate-and-start.js` uses `prisma db push --accept-data-loss` (data loss risk; not suitable for production).
- Two Prisma clients are used in the same codebase:
  - Controllers mostly use `src/lib/prisma.js` (singleton with env-validated DATABASE_URL)
  - Auth middleware uses `src/config/database.js` (separate PrismaClient, different config)
  - Risk: multiple connections, inconsistent datasource config, harder debugging, possible pool exhaustion.

### Auth & cookies (END-to-END breaker)
- Refresh flow reads cookies (`req.cookies.refreshToken`) but Express does not register `cookie-parser`, so `req.cookies` will be undefined by default.
- Cookie behavior in production may break cross-site deployments:
  - refresh cookie uses `SameSite=strict` in production; if frontend and API are on different sites/subdomains, refresh can fail.
- Role naming inconsistency:
  - Prisma schema + middleware conventions are uppercase roles (e.g., ADMIN/SUPER_ADMIN)
  - `register` sets `role: 'user'` (lowercase) which is likely incompatible with RBAC expectations.

### Env vars & configuration
- CORS mismatch:
  - Runtime uses `ALLOWED_ORIGINS` in `src/index.js`
  - Env validation defines `FRONTEND_URL` but does not validate/require `ALLOWED_ORIGINS`
  - Risk: production CORS blocks real browser requests or runs with unvalidated values.
- Email env mismatch:
  - `.env.example` uses `SMTP_HOST/SMTP_USER/...`
  - Code and env validation use `EMAIL_HOST/EMAIL_USER/...`
  - Risk: production email silently “simulates” sending due to transporter misconfig.
- JWT env mismatch:
  - `.env.example` defines `JWT_EXPIRES_IN`, `REFRESH_TOKEN_SECRET`, `REFRESH_TOKEN_EXPIRES_IN`
  - Code hardcodes access expiry `15m` and refresh expiry 7 days; refresh tokens are random bytes (no refresh secret used).
  - Env validator expects `JWT_EXPIRE` (not `JWT_EXPIRES_IN`) and does not validate refresh-token vars.
- AI/OpenRouter env mismatch:
  - `.env.example` includes `OPENROUTER_API_KEY`
  - Env validation does not validate it, but services depend on it.

### Error handling & API contracts
- Global error handler status-code bug (operator precedence) can incorrectly turn many server errors into 400 responses.
- Mixed response formats:
  - Some code uses `{ success, message, data }` helper functions
  - Controllers use `ApiResponse/ApiError`
  - Tests assume specific shapes (e.g., `errors` arrays) that current middleware does not provide consistently.

### Validation & security posture
- Input sanitization currently allows `script` tags via DOMPurify `ADD_TAGS`; this is not acceptable for production unless heavily sandboxed.
- Regex-based “SQL injection” blocking can false-positive on legitimate text (risk: random 400s in production for valid content).
- Rate limiting is not shared across instances (no Redis store configured); scaling to multiple containers weakens protection.

### Background jobs / services correctness
- OpenRouter service fallback call is incorrect (wrong argument order), so fallback behavior can break AI features under error conditions.
- Graceful shutdown tries to check `cacheService.client`, but cache service does not export `client`; Redis may not close cleanly.

### Docs/tests mismatch (quality & safety)
- Backend README references non-existent scripts (e.g. `npm run prisma:migrate`, `npm run prisma:generate`) while `package.json` defines `db:migrate`, `db:generate`.
- Jest config loads `.env.test` but file is missing.
- Tests reference wrong auth endpoints (`/refresh`, `/me` vs actual `/refresh-token`, `/profile`).

## 2) Production hardening change list (ordered, end-to-end)

### Phase A — Make it deployable & predictable
1) Standardize “one truth” for PORT and healthcheck:
   - Choose canonical port (recommend 5000 across env default + Dockerfile + compose + app)
   - Update Docker EXPOSE/HEALTHCHECK and app default accordingly.
2) Fix logging for containers:
   - Default to stdout/stderr in production
   - Make file transports optional (only if `LOG_TO_FILE=true` and directory exists), or create writable `logs/` directory in container.
3) Remove/disable Railway-specific runtime artifacts:
   - Remove `railway.json` from the production path (or keep but mark unused)
   - Replace `migrate-and-start.js` with a safe production entrypoint (see DB phase).

### Phase B — Make DB layer production-grade (Postgres + migrations)
4) Switch Prisma schema to Postgres for production:
   - Make `prisma/schema.prisma` use Postgres provider (use existing `schema.postgres.prisma` content).
5) Replace `db push --accept-data-loss` with migrations:
   - Local/dev: `prisma migrate dev`
   - Prod: `prisma migrate deploy`
6) Unify Prisma client:
   - Remove `src/config/database.js` usage (or make it re-export `src/lib/prisma.js`)
   - Update imports across middleware/controllers to use one shared Prisma instance.

### Phase C — Fix auth end-to-end (cookies, roles, CORS)
7) Add cookie parsing and confirm refresh flow:
   - Add `cookie-parser` middleware
   - Ensure refresh endpoint works using HttpOnly cookie only (no body token needed).
8) Normalize roles:
   - Decide on role set (ADMIN/SUPER_ADMIN/EDITOR/user)
   - Align `register` role assignment and auth middleware expectations.
9) Fix CORS/env alignment:
   - Decide on `ALLOWED_ORIGINS` vs `FRONTEND_URL` approach
   - Validate and enforce it in `config/env.js`
   - Ensure `credentials: true` + allowed origins work in production.
10) Adjust cookie SameSite strategy based on deployment topology:
   - Same-site frontend+api: strict/lax OK
   - Cross-site: requires `SameSite=None; Secure` and careful domain setup.

### Phase D — Security hardening (safe by default)
11) Remove `script` tag allowance in sanitization:
   - Keep safe HTML subset, add explicit allowlist for embeds if required.
12) Rework injection prevention:
   - Make regex detection less aggressive or restrict to specific fields
   - Prefer strict validation schemas + business-rule validation.
13) Make rate limiting production-ready:
   - Add Redis-backed rate limiter store when `REDIS_URL` exists
   - Keep memory fallback only for local/dev.

### Phase E — Reliability, correctness, tests
14) Fix global error handler status logic and unify API error shape:
   - Ensure consistent `{ success, message, data?, errors? }` contract.
15) Fix service bugs impacting production behavior:
   - OpenRouter fallback call
   - Graceful shutdown cache close logic.
16) Repair tests to reflect actual endpoints and env:
   - Add `.env.test` + isolated test DB strategy
   - Update test routes (`/refresh-token`, `/profile`)
   - Ensure tests run in CI/local Docker.
17) Update backend README/docs to match real scripts and env names.

## 3) Verification checklist (what “end-to-end working” means)
- `docker-compose up` brings up API + Postgres + Redis and `/health` returns 200.
- `/api/users` → `/api/users/login` sets refresh cookie and returns access token.
- `/api/auth/refresh-token` works with cookie only (no body token) and rotates refresh token in DB.
- Protected endpoint access with Bearer token works; role-based endpoints enforce roles correctly.
- Logs are visible in container stdout and do not crash due to file permissions.
- Prisma uses Postgres provider; prod uses `migrate deploy` (no `accept-data-loss`).
- Test suite runs and matches real endpoint paths and response schema.
